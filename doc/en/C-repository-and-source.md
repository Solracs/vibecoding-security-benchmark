# Appendix C — Repository and source code

The thirty implementations evaluated in this work — ten sets of three modules —
are not reproduced as listings: they are published, together with the application
framework, the statements handed to the models and the audit tool, in the
project's public repository:

<https://github.com/Solracs/vibecoding-security-benchmark>

Two reasons for this. The first is volume: the evaluated material exceeds seven
thousand lines of code, whose full transcription would be unmanageable and of
little use to the reader. The second, and more important, is that the object of
study is not a text but an **executable artefact**: published this way it can be
cloned, started and re-audited under the conditions described in
[appendix B](B-testbed-manual.md), which is how it should be examined.

## C.1 Obtaining the material

```bash
git clone https://github.com/Solracs/vibecoding-security-benchmark.git
```

All results in this memoir correspond to the state of the repository at commit
**`0cc45ad`** on branch `main`, dated 12 August 2026. To land exactly on that
version, and not on whatever state the repository may present later:

```bash
git checkout 0cc45ad
```

Relevant directories:

```
src/implementations/<implementation>/   modules generated by each model
openspec/specs/hacker-shop/             specification (appendix A)
openspec/prompts/                       per-round statements
tools/audit.js                          audit battery (appendix B)
```

The modules are already laid out in the directory structure the framework
expects, so the audit battery can be run on the freshly cloned material with no
further preparation.

## C.2 Index of implementations

Each implementation contains the same three module names — `auth.js`, `cart.js`
and `profile.js` — and is distinguished only by its containing directory, under
`src/implementations/`.

| Implementation directory | Round | Model |
|--------------------------|-------|-------|
| `gpt` | — | Deliberately vulnerable reference (positive control) |
| `chatgpt-intant` | R0 | GPT-5.5 Instant |
| `gemini` | R0 | Gemini 3.5 Flash Lite |

| `gemini-3.5-flash-lite-R1` | R1 | Gemini 3.5 Flash Lite |
| `hiku-4.5-R1` | R1 | Claude Haiku 4.5 |

| `gemini-3.5-flash-lite-R3` | R3b | Gemini 3.5 Flash Lite |

**Note on the `-R3` suffix.** It corresponds to the **R3b** generation, i.e. the
one obtained with the revised specification documenting the identity contract.
The earlier R3a generation was overwritten on disk when the new one was brought
in and therefore does not appear in the repository: it survives through the
results and logs of that run, and its analysis is in
[chapter 8](08-guidelines-and-improvement.md).

## C.3 Warning about the integrity of the material

**None of the ten generated implementations was hand-edited at any point of the
study**: they are exactly the output each model produced from its round's
statement. This condition is essential to the validity of the comparison, since
any manual correction would have destroyed the object of measurement.

`src/implementations/gpt/` must be expressly excluded from that statement. The
reference implementation is not an experimental generation but the positive
control of the measuring instrument, and its code *was* deliberately modified to
guarantee that the nine attacks have a target that does not defend them. It is
the only hand-touched material in the whole project.

The typos visible in the directory names — `chatgpt-intant` and `hiku-4.5` — are
deliberately preserved for consistency with the identifiers used while capturing
the results.

The repository history allows this to be verified: each set of modules was
brought in as a single commit, with no later touch-ups to the generated code.
