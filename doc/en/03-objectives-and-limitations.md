# 3. Objectives and limitations

Stating the limitations is not a formality: in a comparative study, bounding the
variables is the condition that guarantees the internal validity of the
conclusions.

## 3.1 Objectives

**General objective.** Design and validate a *reproducible security benchmark
that compares, against one and the same functional specification, the security of
the code generated by different language models*.

| Id | Specific objective | Covered in |
|----|--------------------|------------|
| **O1** | Design a modular web architecture that separates the framework (routing, sessions, persistence, views) from the business logic, so the latter can be swapped at runtime without touching the rest of the system. | [Ch. 5](05-solution-design.md) |
| **O2** | Define a single, unambiguous functional specification — a module contract with fixed signatures — handed identically to every model, so all implementations pursue identical requirements and are therefore comparable. | [Ch. 5](05-solution-design.md), [App. A](A-specification-and-prompts.md) |
| **O3** | Generate, from that specification and without deliberately inducing *or* avoiding vulnerabilities, the implementations of several language models, preserving the genuine character of their output. | [Ch. 6](06-generated-code.md) |
| **O4** | Package the solution in a reproducible container guaranteeing identical execution conditions for every implementation. | [Ch. 5](05-solution-design.md) |
| **O5** | Design and execute a set of representative web attacks, traced against the OWASP Top 10 and the CWE catalogue, and evaluate each implementation homogeneously and with documented evidence. | [Ch. 7](07-vulnerability-analysis.md) |
| **O6** | Analyse the results comparatively and identify, at code level, the causes of the vulnerabilities found and of the effective defences. | [Ch. 7](07-vulnerability-analysis.md) |
| **O7** | Design and execute a round-based remediation experiment measuring how much specificity the security guidance needs before a vulnerability class disappears, and at what functional cost. | [Ch. 8](08-guidelines-and-improvement.md) |
| **O8** | Derive from the analysis a set of security guidelines applicable to AI-assisted code generation. | [Ch. 8](08-guidelines-and-improvement.md) |

## 3.2 Limitations and scope

The scope is deliberately bounded. The following limitations are assumed and
expressly declared:

- **Single domain.** The reference application is an e-commerce site centred on
  user-facing services and payments. Conclusions are circumscribed to this
  domain; extrapolating to other application types must be done with caution.
- **Bounded surface.** Only the business-logic modules of the contract
  (authentication, cart and profile) are evaluated. The framework stays fixed and
  is not part of the model-to-model comparison, although its own weaknesses are
  documented where they matter for interpreting a result.
- **Number of models.** Three AI-generated implementations are compared, plus a
  deliberately vulnerable reference implementation used as a baseline control.
  The goal is to illustrate the methodology and evidence differences, not to
  produce an exhaustive ranking of the model market.
- **One generation per cell.** Every model × round combination comes from a
  single generation. Given the stochastic nature of these systems, it is not
  possible to distinguish "the model fixes the defect" from "this generation
  fixed it". This is the study's most relevant methodological limitation and it
  conditions the strength of the quantitative conclusions.
- **Limited observability of the race condition.** Exploiting attack 4.1 depends
  on the timing of concurrent requests, and the testbed keeps no order records:
  since checkout merely empties the cart, the "several purchases for the price of
  one" effect is not directly observable and must be inferred from the amount
  charged together with the update pattern used.
- **R3b is not a blind replication.** The wording of the revised specification
  was chosen *after* observing the previous round's failure mode, so it is a
  targeted correction and not an independent replication.
- **Single interaction mode.** All implementations were obtained by conversation
  in each model's public web interface. Editor-integrated development agents —
  which execute the code, read its errors and iterate before answering — were not
  evaluated. Their security outcome could differ, and that comparison remains
  future work.
- **Lightweight persistence.** The data layer uses SQLite, whose serialised write
  model conditions the observable behaviour of some transactional
  vulnerabilities.
