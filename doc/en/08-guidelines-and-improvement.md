# 8. Security guidance to the AI, and improvement analysis

The previous chapters characterised the security of the code models generate when
given only a functional specification. This chapter tackles the complementary and
more practically valuable question: **what must one tell a model so it produces
secure code, and what side effects does telling it have?** A round-based
remediation experiment was designed to answer it.

## 8.1 Synthesis of the baseline

Several observations follow from the baseline analysis.

**First**, SQL injection vulnerabilities were systematically avoided by all three
evaluated implementations, suggesting parameterised queries are a well
internalised pattern in current models — probably because of their ubiquity in
training material and best-practice guides.

**Second**, series 3 reveals a transversal weakness: all three implementations
are vulnerable to all four profile attacks. Significantly, the access-control
failure is conditioned by the framework contract itself, which hands over the
target identifier from the URL without verification; no implementation
reintroduced the ownership check from the session, which was within reach. This
pattern suggests **models tend to implement the nominal flow described by the
specification and not to add security controls it does not explicitly request**.

**Third**, series 4 discriminates sharply between implementations. An apparently
minor detail — the `total > 0` check and the use of an atomic decrement — makes
the difference between resisting the business-logic and concurrency attacks or
not. Likewise, the presence or omission of the ownership clause in the delete
determines the outcome of attack 4.2.

These observations sustain the starting thesis: the security of autogenerated
code is neither uniform nor predictable from mere functional correctness, and it
depends on concrete implementation decisions that a modular benchmark such as the
one proposed is able to isolate and measure.

### Contrast with public evaluation frameworks

Of the twenty-seven baseline cells (three implementations × nine attacks),
**seventeen were vulnerable — 63 %**: the twelve of series 3, the four
corresponding to attacks 4.0 and 4.1 in `gemini` and `haiku-4.5`, and the one for
attack 4.2 in `haiku-4.5`.

Pearce et al. (2022) placed at around 40 % the proportion of vulnerable programs
generated by Copilot in security-sensitive scenarios, and BaxBench compromised
roughly half of the functionally correct backend applications. The result
obtained here is therefore of the same order of magnitude as the two works that
have measured the same thing by different routes, and slightly higher — coherent
with a testbed whose nine attacks were chosen to cover the surface of an
e-commerce application rather than to sample the full CWE catalogue.

The most illustrative contrast, however, is with functional-correctness
benchmarks. The three models evaluated score high and comparably on HumanEval and
SWE-bench; yet all three distribute very unevenly across the nine attacks,
between `chatgpt-instant`'s four vulnerable cells and `haiku-4.5`'s seven. **That
divergence between one axis and the other is exactly the gap this work
measures.** Conversely, security-oriented datasets operate on isolated fragments
and static analysis, so results such as attack 4.1 (a race between two concurrent
requests) or 4.2 (deleting someone else's cart) fall outside their reach by
construction.

These figures are not directly comparable to each other. Language, task, unit of
analysis (fragment, full application, swapped module) and number of generations
per cell all differ — here it is a single one. The comparison holds as an order of
magnitude and a direction of finding, never as a score.

## 8.2 Design of the remediation experiment

The experiment holds the functional specification constant and varies only the
security guidance accompanying it. Comparing rounds measures how much specificity
is needed before a vulnerability class disappears. Four rounds were run:

- **R0 (baseline).** Functional specification only. This is the material analysed
  in chapters [6](06-generated-code.md) and [7](07-vulnerability-analysis.md).
- **R1 (generic directive).** The specification plus one sentence with no
  specific content: *"Implement it securely, following current web application
  security best practices."* Measures whether a zero-cost instruction produces
  any effect at all.
- **R3a (vulnerability report).** The specification plus the model's own audit
  report: for each defect found, its description, location, CWE/OWASP
  classification and the evidence for it. Measures the ceiling of remediation
  capability.
- **R3b (report plus environment contract).** Identical to R3a except for one
  thing: the specification explicitly documents how the framework exposes the
  authenticated identity.

Three methodological decisions condition the validity of the experiment:

- **The reports do not prescribe the fix.** Each finding states what fails, where,
  and how it was demonstrated — never how to correct it. If the statement
  contained the fix, the experiment would measure the quality of the advice and
  not the model's capability.
- **Each model receives only its own findings.** Reports are generated separately
  and omit the attacks that model passed. A shared report would leak results
  between subjects and turn the task into "fix this list" instead of "fix your
  own defects".
- **No generation knows about the previous ones.** Each implementation is
  obtained in a fresh conversation, with no history and with cross-conversation
  memory features disabled. Otherwise what would be measured is accumulated
  conversation, not the level of guidance.

**No generated implementation was ever hand-edited.** When an answer was
unusable, it was recorded as a failed generation and repeated; correcting the
code manually would have destroyed the very object of measurement. The only
exception is the `gpt` reference implementation, which is not an experimental
generation but the instrument's positive control and was modified on purpose.

## 8.3 The generic directive: a real but narrow effect

**R1 is not a null result.** The generic instruction produced two verifiable
changes:

- **Filename sanitising.** All three implementations began normalising the
  received upload name, so attack 3.2 (path traversal) stopped succeeding in all
  three.
- **Unrequested password hashing.** Two of the three added `bcrypt` for storing
  and verifying passwords. The specification mentions hashing nowhere and the
  baseline stored passwords in cleartext, so this is a genuine security
  improvement induced by the directive.

The reach of the improvement is nevertheless very limited. Three of the four
profile attacks persist in all three implementations: broken access control
(3.0), stored XSS (3.1) and executable SVG upload (3.3).

**The most revealing contrast happens inside a single function.** All three
implementations sanitised the uploaded file's path and none validated its type,
both defences being contiguous lines of the same upload-handling block. The
proposed interpretation is that a generic directive **activates named defensive
idioms** — parameterised queries, `path.basename`, password hashing — widely
associated in training data with the word "security", **but does not induce
systematic reasoning about the attack surface** of the feature being implemented.

The round also left a functional regression. Of the two implementations that
added password hashing, one accounted for pre-existing rows with cleartext
passwords and the other did not, so the latter completely prevented
authentication of the already-seeded accounts. Same directive, same added
feature, opposite outcomes.

## 8.4 The R3a collapse: security obtained by destroying functionality

R3a produced, at first sight, an unbeatable result: **26 of the 27 attack cells
became secure** and two of the three implementations came out clean across all
nine attacks. At second sight the result is a failure: **all three
implementations completely disabled the profile update**. No user — neither the
attacker nor the legitimate owner — could modify their bio any more. Broken access
control (3.0) did not disappear because it was fixed, but because the function it
lived in stopped working.

Two of the three also **fail silently**: they return the success redirect the
specification requires and write nothing. The user would see their dashboard
reload with the previous bio and no error message.

### Root cause: an invented session object

All three implementations added the ownership check the report demanded, and all
three wrote it against **a session object that does not exist**. The framework
stores the identity as a plain string holding the username:

```js
req.session.user = username        // e.g. "admin" — a string
```

whereas the implementations queried, respectively, `session.userId`,
`session.username` and `session.user.id` (a property of a string). In all three
cases the comparison is never satisfied, so the guard denies every request,
including the owner's.

### Why the models could not have known

The original specification does not describe the session object: it mentions it
once, to say it belongs to the framework. The vulnerability report, for its part,
states the defect without naming the property, by design. The models were
therefore asked to impose an ownership relation on an identity they had no
documented way to read, and all three resolved the gap by **inventing a plausible
interface and never verifying it**. The guesses are individually reasonable —
`session.userId` and `session.username` are conventional names — and uniformly
wrong.

The relevant failure, and the one that gives this finding transferable value, is
not that the model wrote an insecure check: it is that **it wrote a check it
never once executed**. A single manual run of the feature would have exposed it.

## 8.5 R3b: the controlled comparison

To discriminate between the two possible explanations of the collapse —
inability to implement access control, or absence of documentation of the
environment contract — the round was repeated modifying a single variable. The
revised specification documents what the session contains and warns that the
database holds prior rows with cleartext passwords. **No requirement was added,
removed or reformulated, no fix was prescribed, and the findings delivered were
byte-for-byte identical.**

The result is unequivocal: **all three implementations came out clean across the
nine attacks and passed the five functional checks. R3b is the only configuration
in the whole study with zero vulnerabilities and zero functional regressions.**

The decisive check is a cross one, because rejecting every update *also* passes
attack 3.0. The audit therefore verifies both halves of the same property in the
same run: the attacker is rejected **and** the owner is admitted. All three
implementations satisfy both conditions, so what is observed is correct access
control and not a disabled endpoint.

It follows that the R3a collapse **was not due to an inability to implement
access control**. With the identity contract written down, all three models
implemented it correctly on the first attempt and with no other change to the
statement.

### Threat to validity

The revised specification explicitly names the three properties that *do not*
exist — precisely the ones the models invented in R3a. That wording was chosen
after observing R3a, so R3b is not a blind replication but a targeted correction
of a known failure mode. It demonstrates that the models *can* implement the check
correctly when the contract is available; it does not demonstrate they would have
discovered it from neutral wording. A stricter replication would document
`req.session.user` positively, without the negations. This limitation must be
kept in mind when interpreting the size of the effect.

## 8.6 Quantitative improvement analysis

Over 27 attack cells (three implementations × nine attacks), the vulnerability
count evolves **17 → 10 → 0** across baseline, generic round and report round.

Reading that series in isolation leads to the wrong conclusion. The series that
corrects it is that of **functional regressions**, which follows the inverse
trajectory: **0 → 1 → 3 → 0**. In R3a, the minimum of vulnerabilities coincides
with the maximum of destroyed functionality.

| | R0 | R1 | R3a | R3b |
|---|----|----|-----|-----|
| Vulnerabilities (of 27) | 17 | 10 | 0 | **0** |
| Implementations with broken functionality | 0 | 1 | 3 | **0** |

From this double series comes the chapter's central reading: the evaluated models
behave as **good remediators and poor auditors**. When told exactly what is wrong,
they fix it; when left to find it, they apply only the idioms a defensively-toned
statement evokes. And they act on what they are told aggressively, without
verifying that their fix preserves functionality.

Per-model progression and the full per-round matrices are in
[results.md](results.md).

## 8.7 Proposed guidelines

The following guidelines follow from the results, applicable to any AI-assisted
development workflow that incorporates security fixes. They are stated in order
of importance according to the evidence gathered.

**D1. No AI-generated security fix should be accepted without a functional
regression test.** This is the guideline with the strongest empirical backing in
this work: in R3a all three implementations reached a near-perfect security
matrix by disabling the functionality, and two of them did so while returning a
success code. An analysis that only counts vulnerabilities — static or dynamic —
would rate that result as impeccable remediation.

**D2. Explicitly document the environment contract, especially how the
authenticated identity is obtained.** A remediation instruction is worth whatever
the environment contract it is written against is worth. Neither the model nor
the vulnerability report will surface the gap: only running the feature will. The
difference between R3a and R3b is exactly this point.

**D3. Do not rely on generic security instructions.** "Implement it securely"
produces a real but narrow effect, concentrated on named defences. It does not
cover reasoning about the concrete attack surface: in R1 the file path was
sanitised and the file type was not validated, on contiguous lines.

**D4. Verify which layer the defence is applied at.** The R3 implementations
neutralised cross-site scripting by escaping at write time. It works in this
application because they were told the views were out of their reach, but it is
the wrong layer: it corrupts the stored datum for any other consumer and is not
what standard practice recommends, which is contextual encoding on output. **An
effective fix can still be architecturally wrong.**

**D5. Watch for silent failure modes.** Two of the three R3a implementations
returned HTTP 302 to the success page having written nothing. Checks limited to
verifying status codes do not detect this class of regression; the observable
effect on system state must be checked.

**D6. Account for pre-existing data when changing a security mechanism.** In R1,
two implementations added password hashing; one accounted for the inherited
cleartext rows and the other broke authentication entirely. Any change to
credential storage must keep working for data that already exists.

**D7. Validate the measuring instrument before trusting its results.** A
methodological guideline aimed at whoever audits. An automated battery that fails
to reach the application returns "secure" everywhere, a result indistinguishable
from success. Keeping a deliberately vulnerable implementation in the testbed and
requiring the battery to detect it is the cheapest way to rule out that failure;
in this work it prevented an entirely invalid run from being accepted.

> **D1, D5 and D7 share a practical consequence:** in an AI-assisted workflow,
> verification cannot be delegated to the same agent that produces the change,
> nor reduced to a fresh analysis of the code. It must execute the system and
> observe its behaviour.
