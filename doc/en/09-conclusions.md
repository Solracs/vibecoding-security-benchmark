# 9. Conclusions and future work

## 9.1 Objectives revisited

**O1 and O2 (modular architecture and single contract).** A web application was
built in which the framework — routing, sessions, persistence and views — stays
fixed and the business logic is swapped at runtime through a stable module
contract. Dynamic discovery of implementations from directory names allowed ten
successive implementations to be incorporated without modifying a single line of
the framework.

**O3 (undirected generation).** Implementations of three models were generated
across four rounds of increasing guidance, without deliberately inducing or
avoiding vulnerabilities and without hand-editing any output.

**O4 (reproducible container).** The solution is packaged in a container image
that automatically incorporates any added implementation.

**O5 and O6 (attacks and analysis).** A battery of nine attacks traced against
the OWASP Top 10 and the CWE catalogue was designed and executed, first manually
with an intercepting proxy and then automatically. Agreement between both methods
on all nine attacks sustains the validity of the instrument. Attack 4.1 required
fixing the verdict criterion beforehand, as a first version of the instrument
applied one different from the manual measurement; once resolved, both methods
agree.

**O7 (remediation experiment).** Four rounds of increasing guidance were run on
three models, measuring in each both the vulnerabilities remediated and the
functional cost of the remediation.

**O8 (guidelines).** Seven guidelines were derived from the analysis, headed by
the requirement that every AI-generated security fix be accompanied by a
functional regression test.

## 9.2 Substantive conclusions

1. **The security of autogenerated code is neither uniform nor predictable from
   functional correctness.** Every evaluated implementation passes the
   specification's functional tests and none of the baseline resists the full
   attack battery. Minimal implementation differences — the presence of an
   ownership clause in a delete, a sign check before a charge — separate the
   secure outcome from the vulnerable one.

2. **Current models are good remediators and poor auditors.** Given a specific
   report they fix practically everything pointed out to them; given a generic
   instruction they apply only stock defences. The distance between those two
   behaviours is the work's central quantitative finding.

3. **A security fix can make the system worse.** The R3a collapse demonstrates
   that a vulnerability can be closed by destroying the functionality that
   contained it, and that this result is indistinguishable from success for any
   metric that only counts vulnerabilities.

4. **Incomplete documentation of the environment turns a correct intention into a
   silent breakage.** The controlled comparison between R3a and R3b isolates this
   cause: same models, same report, same defect list, and the only difference is
   whether the identity contract was written down.

## 9.3 Contributions

- **Methodological.** A benchmark design that fixes the framework and swaps only
  the business-logic modules, isolating each model's contribution and making the
  implementations comparable line by line against one specification.
- **Instrumental.** An automated audit battery that runs the nine attacks plus a
  functional regression test on any implementation, with validation of the
  instrument itself through a deliberately vulnerable reference.
- **Empirical.** The round-based remediation experiment and the seven derived
  guidelines — in particular the documented evidence that a remediation can reach
  a perfect security matrix by destroying the functionality.

## 9.4 Future work

### Closing the current limitations

- **Repetitions.** Every cell of the study comes from a single generation. Given
  the stochastic nature of the models, repeating each model × round combination
  at least three times would allow distinguishing "the model fixes it" from "this
  generation fixed it" and reporting variance. This is the most important
  methodological gap left open.
- **Order records in the testbed.** Checkout merely empties the cart, leaving no
  record of the purchase. Adding an orders table would make the "several
  purchases for the price of one" effect directly observable and remove the need
  to inspect the update pattern in order to classify attack 4.1.
- **Strengthening attack 2.0.** It is the only attack without a positive control.
  Adding a reference implementation with a vulnerable registration would
  establish that the vector is real and raise the evidential strength of its
  result.
- **Blind replication of R3b.** Document the session contract positively, without
  enumerating the non-existent properties, to measure the effect free of the bias
  of having previously observed the failure mode.

### Extensions of the experiment

- **Guidance delivery mode.** In a real vibe-coding workflow, guidelines are
  delivered as project rule files rather than as statement text. Comparing both
  modes would measure whether the channel affects compliance.
- **Development agents versus conversational interfaces.** All implementations
  here were obtained by pasting the statement into each model's web interface.
  Editor-integrated development agents operate differently: they read the rest of
  the project, execute the code and fix their own errors before delivering an
  answer. Repeating the experiment in that mode would measure whether the ability
  to run what one writes alters the observed vulnerability profile — today the
  most practically interesting question this work leaves open.
- **Widening the panel and the domain.** Adding more models, and replicating the
  methodology on a different domain, would test how far the conclusions depend on
  the e-commerce scenario used.
- **Auditing the framework itself.** The work kept the framework out of the
  comparison, but it contains weaknesses of its own — an unauthenticated admin
  endpoint, a hardcoded session secret, unescaped views — whose treatment by the
  models would be the object of a complementary study.
