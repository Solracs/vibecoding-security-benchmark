# 1. Introduction and motivation

Since the first compilers, the history of software development reads as a
succession of abstraction layers that moved work from the programmer to the
machine: high-level languages, garbage collectors, IDEs, autocompletion.
Generative AI is the most recent and by far the widest-reaching link in that
chain, because for the first time the *writing* of code — not only its editing or
verification — is partly delegated to an automatic system.

The shift is not marginal. The annual Stack Overflow developer survey (2025)
reports that **84 % of developers use or plan to use AI assistants** in their
workflow, while only **29 % say they trust the correctness of the output** those
systems produce. That gap between near-universal adoption and minority trust is
the starting point of this work: practice has run ahead of guarantees.

## 1.1 The vibe coding paradigm

The working style in which a developer describes in natural language what they
want and accepts the model's suggestions with minimal supervision has been
informally named *vibe coding* (Karpathy, 2025; Sarkar, 2025). The developer's
role moves from technical implementation towards product direction: a high-level
reviewer who steers the model, validates results and chains iterations, while the
translation from intent to code falls to the system. The immediate consequence is
a marked acceleration of prototyping, associated with measurable productivity
gains (Peng et al., 2023).

That same delegation introduces a structural risk. A language model optimises the
plausibility of its output from patterns observed in its training data; it does
not natively reason about the security properties of the code it produces. When
that data contains — as it inevitably does — an abundance of insecure code, the
model reproduces those same patterns. Automatic generation therefore prioritises
immediate functionality, whatever "makes the program work", over architectural
robustness and defensive security, which are rarely visible in a superficial run.

## 1.2 The security problem in autogenerated code

The academic literature has repeatedly documented that LLM-based assistants
replicate, and even amplify, the insecure patterns present in their training
data: Pearce et al. (2022) on GitHub Copilot suggestions, Khoury et al. (2023) on
ChatGPT-produced code, and Fu et al. (2025) on real GitHub-hosted projects. Code
generated without strict human review frequently carries classic weaknesses:
injections arising from string-concatenated queries, access-control failures that
skip the ownership check, race conditions in transactional logic, or unvalidated
file uploads. These are, for the most part, well-known weaknesses catalogued for
years in frameworks such as the OWASP Top 10 or the CWE — and still present in
the code generated today.

The risk is aggravated by an experimentally observed human factor: developers
using AI assistants not only tend to produce less secure code, they are also
*more* confident it is correct (Perry et al., 2023). That combination — greater
exposure plus lower risk perception — is especially dangerous in applications
handling sensitive user data or payment flows, which is exactly the kind of
service this work centres on.

## 1.3 Motivation and contribution

The main motivation is to design, build and evaluate a structured security
benchmark that allows auditing, comparing and analysing how different language
models implement the same business logic and how they handle the commonest
security failures.

The central contribution is a design decision: **security is delegated to the
concrete implementation of each feature, not to the framework**. A modular web
application — a fictional e-commerce site called "Hacker Shop" — was developed in
which the framework (routing, sessions, data schema and views) stays fixed while
the business-logic modules are swapped for the implementation each model
generated from a shared specification. Holding everything else constant and
swapping only those modules isolates each model's contribution and lets the
implementations be compared line by line against identical requirements. That
isolation is what distinguishes the approach from other proposals (see
[chapter 2](02-state-of-the-art.md)).

On that basis the work adds a second experimental dimension: a **round-based
remediation experiment** in which each model is handed security guidance of
increasing specificity — from a generic instruction up to its own audit report —
measuring in each case which vulnerabilities disappear and at what cost. That
second dimension underpins the guidelines proposed in
[chapter 8](08-guidelines-and-improvement.md).

In short, the work pursues a double objective: to show empirically and
reproducibly the weaknesses of autogenerated code in a realistic scenario, and to
extract from that analysis a methodology and a set of security guidelines
applicable to AI-assisted code generation.
